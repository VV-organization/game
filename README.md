# FApix Racing

Браузерные гонки на React, Three.js и TypeScript: четыре трассы, заезды с пятью ботами, гараж, каталог из 300 товаров, аккаунты и кошелёк Fapix. Backend — Express и встроенный в Node.js SQLite.

Основа интерфейса — дизайнерский прототип fapixracing.com. Требования экономики и каталога взяты из [VV-136](https://linear.app/finext-io/issue/VV-136). Исходный прайс и результаты исследования сохранены в [docs/research](docs/research/requirements.md).

Сетевая гонка с реальными игроками не реализована. Заезды работают локально в браузере, результаты сохраняются на текущем устройстве. За тренировки Fapix не начисляются.

## Требования

- **Node.js 24**, npm. Разработка и проверки выполнялись на Node 24.17.0.
- Современный браузер с WebGL и аппаратным ускорением.
- Постоянный локальный диск для SQLite при размещении сервера.

Отдельный сервер базы данных не требуется. Используется `node:sqlite`; база и таблицы создаются при первом запуске.

## Локальный запуск

Из корня проекта:

```sh
npm ci
cp .env.example .env
npm run dev
```

Если `.env` уже существует, сохраните его настройки вместо повторного копирования.

Откройте [http://127.0.0.1:5173](http://127.0.0.1:5173). Vite проксирует `/api` на API по адресу `http://127.0.0.1:3001`. Для стандартного запуска разработки оставьте `PORT=3001`.

По умолчанию `PAYMENT_MODE=disabled`: гонки, регистрация и каталог доступны, создание платежей отключено.

Для проверки кошелька без настоящих денег явно установите в `.env`:

```dotenv
PAYMENT_MODE=sandbox
```

Перезапустите `npm run dev`. Зарегистрируйте аккаунт, откройте кошелёк, выберите сумму и способ оплаты. После создания тестовой операции доступны кнопки успешной оплаты и отказа. Новый аккаунт всегда начинает с нулевого баланса. Sandbox не обращается к банку или платёжному провайдеру.

Курс: **1 ₽ = 2 Fapix**. Пополнение принимает целые суммы от 1 до 100 000 ₽. Товар покупается отдельно за Fapix после пополнения.

## Проверки и сборка

```sh
npm run format:check
npm test
npm run typecheck
npm run build
```

- `npm run format:check` — проверка форматирования Prettier без изменения файлов; `npm run format` применяет форматирование к исходникам.
- `npm test` — Vitest: экономика, аккаунты, идемпотентность, провайдер, восстановление кошелька, история, игровые правила и локальные результаты.
- `npm run typecheck` — проверка TypeScript.
- `npm run build` — проверка типов и production-сборка интерфейса в `dist/`.

Проверки платёжного провайдера используют изолированные ответы. Они не создают настоящих платежей и не подтверждают готовность банковской интеграции.

[GitHub Actions](.github/workflows/checks.yml) выполняет `npm ci`, `format:check`, тесты и сборку на Node 24 для push и pull request. Наличие workflow не означает, что удалённый CI уже запускался.

Состояние проверки на 6 ноября 2026 года: 105 тестов, включая автоматическое прохождение всех четырёх трасс через обычные команды газа и поворота — три круга и 48 контрольных точек на каждой. Локально вручную проверены sandbox-пополнение с восстановлением после reload, покупка и экипировка, видимость приобретённого цвета на трассе, пауза/restart и основные мобильные сценарии. В Chrome также проверены горизонтальные экраны 844×390 и 568×320. Структурный аудит всех 300 SKU не выявил одинаковых целевых моделей/материалов; это не заменяет ручную визуальную приёмку каждого товара. Полная матрица результатов и ограничений — [acceptance.md](docs/research/acceptance.md), воспроизводимые ручные проверки — [qa-plan.md](docs/research/qa-plan.md).

## Запуск собранного приложения

```sh
npm ci --include=dev
npm run build
npm start
```

Сервер раздаёт `dist/` и API на одном адресе, по умолчанию `127.0.0.1:3001`. `npm start` устанавливает `NODE_ENV=production`.

В текущей структуре сервер запускается через `tsx`, который находится в devDependencies. Поэтому для production-запуска нужны зависимости, установленные с `--include=dev`; установка с `--omit=dev` не подходит.

Production предполагает HTTPS. Secure-cookie сессии нельзя проверять как обычную HTTP-установку на произвольном домене; для локальной разработки используйте `npm run dev`.

## Настройка Arco Pay

Реальный режим включается только явно:

```dotenv
PAYMENT_MODE=arco
PUBLIC_URL=https://your-racing-domain.example
ARCO_PAY_SHOP_ID=your_shop_id
ARCO_PAY_API_KEY=your_api_key
ARCO_PAY_BEARER_TOKEN=your_bearer_token
ARCO_PAY_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----"
```

Значения выше — обозначения, не рабочие ключи. Используйте собственные данные мерчанта этого проекта. Секреты не должны попадать в git, клиентскую сборку или логи.

`PUBLIC_URL` — внешний HTTPS-origin без пути, query-параметров и fragment. Он используется для проверки источника запросов, callback и возврата после оплаты.

Адаптер реализует merchant-протокол **Arco Pay / Clickit**, проверенный по текущему коду соседних витрин:

- API по умолчанию: `https://api.clickit.team/api/v1`.
- Карточная форма: `https://payment.paidlayer.com`.
- СБП: создание IPS-заказа и получение ссылки `https://qr.nspk.ru/...`.
- Callback этого проекта: `PUBLIC_URL/api/payments/arco/callback`.

Это проверка программного контракта, а не успешная проверка живого мерчанта. Рабочие ключи, разрешённые способы оплаты, доступность callback, реальное списание и зачисление ещё требуют проверки в выбранном окружении провайдера. Без полного корректного конфига сервер остаётся в режиме `disabled`.

Адреса можно переопределить через `ARCO_PAY_API_URL` и `ARCO_PAY_PAYMENT_ORIGIN`, если провайдер выдал другой endpoint. Не смешивайте этот контракт с отдельным API `api.arcpay.space/v1`.

Подробности запросов, подписи, статусов и восстановления: [docs/research/payment-integration.md](docs/research/payment-integration.md).

## Размещение и сохранность данных

Для одного production-процесса:

1. Настройте постоянный каталог SQLite с правом записи только сервисному пользователю, например `DATABASE_PATH=/var/lib/fapix-racing/fapix.sqlite`.
2. Установите `PUBLIC_URL` и направьте весь HTTPS-origin через reverse proxy на приложение. API и интерфейс должны оставаться на одном origin.
3. Пропускайте callback на `/api/payments/arco/callback` без изменения тела и заголовка `Payment-Sign`.
4. Запускайте `npm start` под менеджером процессов с перезапуском после сбоя.
5. Проверяйте `GET /api/health`, но отдельно проверяйте регистрацию, сохранность покупок и фактический платёжный путь.

`HOST` по умолчанию равен `127.0.0.1`. В контейнере при необходимости используйте `HOST=0.0.0.0` и постоянный volume для базы. Не храните кошелёк на временной файловой системе контейнера.

Стандартные базы:

| Режим           | Файл по умолчанию           |
| --------------- | --------------------------- |
| disabled / arco | `data/fapix.sqlite`         |
| sandbox         | `data/fapix-sandbox.sqlite` |

База дополнительно хранит признак sandbox/live и откажется использовать sandbox-кошельки для настоящей экономики. Не переносите тестовый баланс в live-базу.

SQLite работает в WAL-режиме. Для резервного копирования работающего приложения используйте согласованную SQLite backup-операцию, а не копирование только основного файла без WAL. Например, при установленной утилите `sqlite3`:

```sh
sqlite3 /var/lib/fapix-racing/fapix.sqlite ".backup '/secure-backups/fapix-racing.sqlite'"
```

Храните резервные копии отдельно от рабочего диска и регулярно проверяйте восстановление. Для нескольких экземпляров приложения потребуется общая транзакционная база и координация фоновой сверки; текущая конфигурация рассчитана на один экземпляр.

## Границы безопасности и функциональности

- Баланс, владение, экипировка и история принадлежат серверному аккаунту. Пароли хешируются scrypt, сессионные токены хранятся в базе в хешированном виде.
- Cookie — HttpOnly и SameSite=Lax; production добавляет Secure. Запросы изменения состояния проверяют origin и JSON-тип. Запросы авторизации и изменения состояния ограничиваются по частоте.
- Покупка и выдача товара выполняются в одной транзакции. Повторный запрос не списывает деньги повторно и не дублирует владение.
- Гость может пополнить указанный аккаунт, но не получает его баланс, инвентарь или авторизацию. Гостевая платёжная сессия создаётся до первого финансового запроса.
- Возврат браузера и содержимое callback сами по себе не подтверждают оплату. Подпись проверяется по исходным байтам, затем сервер независимо запрашивает статус и сверяет заказ, мерчанта, валюту и сумму.
- Только CHARGED и IPS_ACCEPTED дают право на однократное зачисление. Неопределённый CREATE сохраняется для проверки; сервер не создаёт повторную оплату вслепую.
- Browser localStorage используется для локальных результатов гонки, sessionStorage — для восстановления UI оплаты. Они не являются источником баланса.
- Возвраты, чарджбэки, фискальные чеки, восстановление пароля и административная панель не реализованы.

## Структура

| Путь                       | Содержимое                                           |
| -------------------------- | ---------------------------------------------------- |
| `src/components/`          | Лендинг, магазин, авторизация, кошелёк               |
| `src/game/`                | 3D-сцена, симуляция гонки, управление и кастомизация |
| `src/shared/`              | Общие типы                                           |
| `server/`                  | API, SQLite, каталог, интеграция провайдера          |
| `public/assets/reference/` | Локальные референсные изображения, SVG и шрифты      |
| `docs/research/`           | VV-136, прайс, исследование дизайна и платежей       |

Управление в гонке: WASD/стрелки — движение, пробел — дрифт, Shift — ускорение, E — бонус, R — возврат на трассу, Esc — пауза. На мобильном экране доступны сенсорные кнопки.
