# Подтверждение почты при регистрации в Fapix Racing

Игрок регистрируется по логину, паролю и почте. Один раз вводит код из письма и получает игровую сессию. При каждом последующем входе вводит логин и пароль. Обработчик входа работает независимо от Purelymail, в том числе при сбое почты.

## Что видит игрок

1. Кнопка «Зарегистрироваться» принимает логин, пароль и адрес. Когда Purelymail принимает письмо, форма показывает «Введите код из письма на …», поле на шесть цифр и срок действия. Ведущие нули значимы. Код можно вставить целиком.
2. Письмо приходит от `Fapix Racing <support@fapixracing.com>` с темой «Код регистрации в Fapix Racing». В тексте явно указаны код, назначение и срок в 10 минут. Пароль игрока в письмо не включается.
3. На том же экране есть «Изменить почту» на случай опечатки и «Отправить ещё раз» с отсчётом 60 секунд. После обновления страницы сервер возвращает адрес в маске и актуальные сроки по cookie незавершённой регистрации.
4. После верного кода форма закрывается, и игрок возвращается к выбранному заезду или приглашению в комнату. При неверном вводе можно исправить код. При истечении срока или исчерпании пяти попыток форма предлагает запросить новый.

## Переход на новую регистрацию

При выпуске все прежние аккаунты удаляются из рабочей игры. Все игроки регистрируются заново. Старые сессии утрачивают силу. Повторное использование прежнего логина создаёт новый ID с начальным балансом и стандартным гаражом.

Все существующие аккаунты тестовые. Сброс выполняется один раз при выпуске через переключение на пустую рабочую базу SQLite.

## Отправка

Для первого выпуска предлагается прямая отправка с бэкенда через Nodemailer по TLS на `smtp.purelymail.com:465`. Один сервер игры уже обслуживает регистрацию и SQLite. Такой вариант позволяет сразу показать, принял ли Purelymail письмо. Альтернатива с фоновой очередью позволяет пережидать сбои провайдера, но требует отдельного обработчика и защиты содержимого заданий с ещё действующими кодами. Для короткоживущего кода игрок уже может запросить новое письмо.

SMTP-логин, пароль приложения и отдельный ключ HMAC задаются в серверном окружении. В журнал пишутся идентификатор запроса, время и результат SMTP. Пароль, код и текст письма в журнал не попадают. Ответ SMTP означает принятие письма провайдером. Получение письма проверяется отдельно на тестовом ящике.

## Контракт с сервером

| Действие | Поведение |
| --- | --- |
| `POST /api/auth/register` | Проверяет поля, готовит незавершённую регистрацию с хешем пароля и инициирует отправку. Выдаёт отдельную случайную cookie регистрации с HttpOnly, SameSite и Secure в production. Аккаунт для платежей и игровая сессия появляются только при успешном подтверждении. |
| `GET /api/auth/registration` | Восстанавливает состояние формы по cookie. Возвращает адрес в маске, срок действия и время следующей отправки. |
| `POST /api/auth/registration/resend` | Отправляет очередной код для той же регистрации. Позволяет передать исправленный адрес. Перед изменением адреса предупреждает, что понадобится код из нового письма. |
| `POST /api/auth/registration/verify` | По cookie и шестизначному коду атомарно подтверждает адрес, создаёт аккаунт и сессию. |
| `POST /api/auth/login` | Сохраняет текущий контракт с логином и паролем. В ответе о пользователе доступен признак подтверждения для проверки допуска к игре. |

Адрес приватен. В комнате и при пополнении по-прежнему используется игровой логин.

## Одноразовость, повторы и сбои

- Сервер генерирует шесть цифр криптографическим генератором и сохраняет HMAC от идентификатора регистрации, версии отправки, нормализованного адреса и кода. В SQLite хранятся также срок действия, счётчик ошибок и состояние отправки. На подтверждённый нормализованный адрес действует уникальный индекс.
- Повторный запрос в течение 60 секунд возвращает текущие сроки. Параллельные нажатия одной формы объединяются в одну отправку. До SMTP сервер резервирует отправку короткой транзакцией, сетевой вызов выполняет после неё. У незавершённой отправки есть дедлайн для восстановления после перезапуска.
- Новый код заменяет предыдущий только после подтверждённого принятия нового письма провайдером. До этого прежний код действует до своего срока для прежнего адреса. При отказе или тайм-ауте SMTP форма предлагает повторить отправку. Если ответ SMTP потерялся, позднее письмо может содержать неактивный код. Поздний ответ старого запроса не может заменить более свежую версию.
- Сервер проверяет привязку к регистрации, срок, версию и остаток попыток. Пять неверных вводов блокируют код. В дополнение к паузе между письмами предлагаются начальные лимиты в 5 отправок на адрес и 20 на IP в час, включая неудачные отправки. Счётчики сохраняются при перезапуске. При превышении лимита сервер сообщает время следующей попытки.
- В одной транзакции SQLite сервер погашает код и фиксирует подтверждённый адрес с датой подтверждения. Для нового игрока в ту же транзакцию входят проверка уникальности логина и адреса, создание пользователя и сессии. Два параллельных подтверждения создают один аккаунт. Если подтверждение прошло, а ответ потерялся, игрок может сразу войти по логину и паролю.
- Признак подтверждения проверяется при штатном старте тренировки и на сервере при подключении к онлайн-гонке, в том числе по приглашению и при переподключении. Тренировка в нынешней архитектуре исполняется в браузере.

## Приёмка

После сброса проверить, что старая cookie не открывает игру, а прежний логин доступен для новой регистрации. Для новой регистрации проверить верный код, неверные вводы, истечение 10 минут, повторную отправку, исправление адреса и двойное нажатие. Отдельно воспроизвести отказ SMTP при повторе и одновременное подтверждение из двух вкладок. Проверить, что при отключённом SMTP подтверждённый игрок может войти по логину и паролю и начать гонку. Для сквозной проверки использовать согласованный тестовый адрес и ввести код из фактически полученного письма.
