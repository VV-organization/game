2. Use a dedicated account named `qa_<timestamp>`. Record its login, not its password. Begin with zero balance. Do not use a real customer account.
3. Run monetary end-to-end scenarios only in the explicitly labelled sandbox. In disabled mode verify disabled behavior. In live mode, creation/reachability, provider settlement and ledger credit remain separate claims; an unverified payment is not a success.

## Race correctness and mobile

1. Start every circuit, inspect world, return, and start another. Track title, selected art and environment must agree. No stale previous-track world or duplicated WebGL canvas.
2. Finish three legitimate laps. Time, lap and position must be correct; result callback fires once; the record list contains one result. Final standings must use finish time rather than input array order when everyone has progress 3.
3. Cross start backwards/repeatedly and skip a checkpoint: no free lap. Unit tests support this, but document any observed wrong-way behavior separately.
4. Collect and activate turbo, shield and pulse. Item consumes once and effect appears; pulse affects nearby competitors; shield expires; turbo affects speed. No need to infer effect from an icon alone.
5. Lose browser focus during driving; return. Race must be paused, input released, and sound stopped. Restart after finish and after pause. Check stale held keys and pointer capture.
6. On a real/coarse-pointer mobile surface, hold throttle+steering simultaneously, release each independently, drift, boost, activate an item and pause. Confirm brake/reverse/reset are reachable if exposed by the game. No stuck input after pointer cancellation or orientation change.
7. At 390×844 and landscape, inspect HUD overlap, player visibility, control targets and result/pause dialogs. All actions must be reachable without keyboard.
8. Watch performance and the browser console during repeated enter/exit and preview changes. A successful build does not prove WebGL initialization, playable controls or resource cleanup.

## Independent review follow-up (2026-11-06)

After integration changes, `npm test` passed **43 tests across 5 files**. All previously reported render-independent type errors were resolved. Landing now accepts `popularIds`, `catalogError`, and `onRetry`; stable merchandising and visible load recovery are wired by App. Wallet integer-amount validation and registration-context preservation were changed by root. Engine now routes `saved.car` to speed/acceleration/handling tuning, uses shared finish-time ordering, and includes a touch brake control. These are code/test confirmations; browser results still require separate evidence.

The independent payment review used only temporary in-memory application instances and an injected mock gateway. No real provider request, live merchant, persistent account, or production wallet was touched.

- Concurrent guest first requests with the same idempotency key and no visitor cookie each returned 201, creating two distinct local payments. A visitor identity should be established before a guest may create a payment, or another stable guest request identity must be required.
- An ambiguous provider-create error before receipt of provider ID returned 502. Repeating the same key then returned 200/pending with no checkout URL. The gateway create count remained one, and background reconciliation found no candidate because provider ID was absent. This needs merchant-order lookup or a safe same-order retry; creating a fresh local payment is not recovery.
- No unauthorized credit path was found in the reviewed code. Durable transaction boundaries, unique ledger references, authoritative provider status verification, recipient/amount/method/shop/currency checks, and separate sandbox/live databases are in place. This is a bounded code/test assessment, not live settlement verification.

One material catalog/appearance issue remained at this review point: some SKU variants collapse to identical models, and decor product names do not match rendered objects. Specifically `decor-01` tool stand renders a trophy, `decor-02` racing poster renders boxes, and `decor-03` potted palm renders a flag. The engine's four modulo decor props, twelve body combinations, and twenty decal combinations do not establish 20/20/40 distinct item appearances. Recheck after the engine/catalog owners align names and variant geometry/colour.
